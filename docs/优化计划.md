### #3 改动内容

1. `upsertIndexed(skill, existing)` 增加跳过路径：两个调用方（`scanRoot` / `rescanSkill`）在索引前都已加载过该行，直接传入复用，零额外查询。
2. **跳过条件 = 五项全等**：`content_hash`（主文件 SHA-256）+ `updated_at`（主文件 mtime）+ `files_json`（含各文件 mtime/size/editable）+ `display_name`（计算后的最终显示名）+ `real_path`。一致时只 `UPDATE scan_token`（根扫描末尾的陈旧行清理仍能识别该行），不一致才走完整 36 列 UPSERT。
3. `updated_at`/`indexed_at` 语义保留：跳过不刷新两者；文件被 touch（内容不变、mtime 变）仍触发重写，UI"更新时间"保持准确。
4. 有意偏离报告方案的点：

| 报告方案 | 实际做法 | 原因 |
|---|---|---|
| 仅比较 `content_hash` + `mtime` | 增加 `files_json` / `display_name` / `real_path` 比较 | `files_json` 捕获"SKILL.md 未变但 sidecar 变化"（清单/体积/时间）；`display_name` 捕获 claude/custom 宿主 `renameDisplay` 只写 `display:` 设置不动文件的场景；`real_path` 捕获符号链接重定向 |
| 单独 SELECT 查 `content_hash` + `mtime` | 复用调用方已加载的 `existing` 行 | 两个调用点在索引前都已查过该行，避免每 Skill 一次额外查询 |

### #4 改动内容

1. exact 分组保持全量 JS Map（O(n) 已足够便宜）；name 分组仍需全量轻量列（id/name/hash），故不做重复加载。
2. **near 检测按 `content_hash` 折叠为代表行**：内容相同的行 band 键与两两距离完全相同，且副本全部先得 `exact`（优先且不被覆盖），代表行不改变任何行的最终 kind；大量同内容副本的库在 banded LSH 前即被折叠，O(n²) 源头缩小。
3. **band 桶上限 `NEAR_BUCKET_CAP = 50`**：桶满后新行跳过该 band 的比较（仍有其余 3 个 band 的机会），最坏情况由 O(n²) 降为每桶 ≤ 1250 次比较。
4. **hamming 距离改 uint32 对 + popcount**：每行预算 lo/hi 两个整数，内层循环只做 XOR + 位计数，去掉每对 BigInt 分配。
5. 有意偏离报告方案的点：

| 报告方案 | 实际做法 | 原因 |
|---|---|---|
| SQL `GROUP BY` 先缩小 exact 候选集 | 全量四列轻量列加载一次 + JS Map 分组 | name 分组必然需要全量行；exact 的 SQL 预筛不减少任何加载，代表行方案在进程内完成等价去重 |
| 必要时移入 worker 线程 | 未引入 | 桶上限后最坏约 200×n 次整数比较（万级 Skill 约百毫秒），暂无需跨线程；真出现瓶颈时再做 |

6. 兼容性说明：near 组 id（`near-<sha256>`）因代表行成员减少而变化，属内部值（UI 只展示 kind 徽标），无测试依赖；`duplicate_kind` 展示语义逐行不变。

### #6 改动内容（v4 迁移）

1. SQLite 无法 ALTER 加约束，采用官方"重建表"模式：`snapshots` / `actions` / `skill_notes` / `skill_note_images` / `ai_analyses` 各自 `CREATE ..._new`（带 `REFERENCES skills(id) ON DELETE CASCADE`）→ 拷贝 → `DROP` 旧表 → `RENAME` → 重建索引；`skills` 表本身不动（不涉及列变更）。
2. **重建顺序保证 `foreign_keys = ON` 下安全**：旧表全部无约束，`DROP` 不触发引用检查；拷贝 `INSERT ... WHERE skill_id IN (SELECT id FROM skills)` 即一次性孤儿清理，也不产生违规。
3. `actions.skill_id` 可空（历史操作可能无 skill）：FK 允许 NULL，NULL 行不级联、不清理。
4. 行为变化（记录在案）：`roots-service.remove()` 与扫描陈旧行清理（`DELETE FROM skills WHERE scan_token <> ?`）删除 Skill 行时，现在**级联删除**其快照/历史/笔记/图片/AI 分析（此前残留）。trash/restore 走 UPDATE 不触发级联，不受影响。
5. 有意偏离报告方案的点：

| 报告方案 | 实际做法 | 原因 |
|---|---|---|
| "推荐 FK 为主" | FK 为主 + 拷贝时过滤孤儿（无独立 DELETE） | 重建拷贝天然只保留有效行，少一次全表扫描 |
| 服务层显式清理 | 未改 `roots-service.remove()` | FK CASCADE 已覆盖其语义，代码零改动 |

### #7 改动内容

1. 上限常量与运行时清理集中在 `src/main/db/retention.ts`：快照每 skill **20** 条、actions 总量 **5000** 条、AI 分析每 skill **10** 条；迁移 v4 对存量库执行同样上限的一次性清理。
2. 接线：`createSnapshot` → `pruneSnapshots`；`insertAction` → `pruneActions`；AiService 写入事务 → `pruneAnalyses` + `pruneActions`。写入路径持续执行，杜绝再次膨胀。
3. 与"历史页恢复"交互验证：恢复按钮按 `snapshotId` 读快照，被淘汰的旧操作点击后报"快照不存在"（UI 错误提示，不崩溃）；`after_content` 用于 diff 展示，最近 5000 条操作覆盖 UI 需求（history 默认 100 条）。

### #8 改动内容

1. **body_cache 按需读盘**：v5 迁移清空存量；扫描写 `''`；`SkillRepository.get()` 用 `readFileSync + detectTextFormat` 读 `SKILL.md`（同步读盘，调用方零改动，典型文件 <1 ms）。文件缺失/不可读降级为空正文（与扫描诊断口径一致）。读盘还带来顺带收益：详情页正文始终是磁盘最新内容，外部修改无需等重扫。
2. **FTS5 评估结论：不实施**（有意偏离，理由记录）：
   - `unicode61` tokenizer 把连续 CJK 字符视为单个 token，"视觉"无法子串匹配"视觉审计助手"——与现有 LIKE 子串语义不兼容；
   - `trigram` tokenizer 仅支持 ≥3 字符查询，中文 2 字符查询（"视觉""测试"）完全失效；且 trigram 倒排索引体积约为原文 1–2 倍，达不到 #8 "减小 DB 体积"的目标；
   - #1 后 LIKE 已参数化下推 SQL，千级库搜索数十毫秒级；FTS5 的迁移/双写/回填复杂度与收益不成比例。
3. **冗余消除结果**：`body_cache` 与 `search_text` 的双份全文 → 单份（`search_text` 保留，LIKE 搜索语义不变）；DB 体积约减半。
4. 报告中的可选"大快照落磁盘"（#7）与 FTS5 一起维持现状，文档记录。

### #9 改动内容

1. **总量配额**：每 skill 20 MB（`IMAGE_QUOTA_PER_SKILL`），`addImage` 插入前 `SUM(size_bytes)` 校验，超限拒绝并提示（zh/en 文案）。
2. **自定义协议**：`skill-note-image://<id>`（`main.ts` 在 ready 前 `registerSchemesAsPrivileged` 注册 standard+secure；`application.ts` 在窗口创建前 `protocol.handle`）；handler 只接受 UUID 形 id，按 id 查库返回 `Response`（content-type + no-store），不存在 404。
3. **renderer 同步改**：`SkillNoteImage.dataUrl` → `url`；备注正文标记 `skill-note-image:<id>` 渲染为协议 URL；CSP `img-src` 放行 `skill-note-image:`；**两处 URL 安全闸门均需显式放行**——rehype-sanitize schema 的 `protocols.src`（按属性名分组，非标签名）与 ReactMarkdown 内置 `urlTransform`（默认丢弃非白名单协议），其余 URL 仍走默认安全变换。
4. 安全边界与 IPC 一致：id 为服务端生成的 UUID，不可枚举、不可注入；协议 handler 不接触文件系统路径。

### #10 改动内容

1. 用系统 ffmpeg（无 VS 工具链，未引入任何新依赖）压缩：头像照片 → JPEG 质量 ~85（1254×1254 尺寸不变），公众号二维码 → `palettegen/paletteuse` PNG-8 量化（1710×624 尺寸不变、透明保留、微信绿主色逐点一致）。
2. 体积：3.3 MB + 4.3 MB → 291 KB + 75 KB，**省约 7.2 MB**；E2E 的 `naturalWidth/naturalHeight` 精确断言（1254²、1710×624 等）全部保持通过。
3. `AuthorModal.tsx` import 更新为 `.jpg`；webpack asset 规则已覆盖 jpg。
